### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then leave the queue alone.**

This is the half after `skill://sky-mode/playbooks/babysit.md`. A green check or approving bot is not an independent verdict. Shipping requires user authorization to land the specified PRs and repository permission. It does not grant force-push, policy-bypass, deployment, branch deletion or unrelated publishing authority.

1. **Resolve the forge, then verify every PR independently.** `gh` is the default. Prefer installed Origin only when it resolves the repository and its documented interface is available; read its installed help before using it. Otherwise record the fallback. Keep one forge for view, watch, edit and merge; Graphite is not required. Freeze the actual bottom-to-top base-branch chain and identify independent work separately.

   Assign one independent verifier per PR, not one agent covering the whole stack. Scope inline first. For two or more substantial independent verifications, use one native `task` batch, one item per PR, with `# Goal`, `# Constraints`, and `# Contract` in shared context and `# Target`, `# Change`, and `# Acceptance` in each assignment. Use the configured general task agent for real-surface execution and the custom per-PR verdict below, or a discovered specialist explicitly compatible with that assignment, its tools and output contract. Bundled `reviewer` can only supply a separate bounded review of patch-introduced bugs anchored to changed diff lines in its native findings/overall_correctness/explanation/confidence schema. `security-reviewer` can supply only a compatible source-security slice in its own schema. A schema override cannot make a patch-only reviewer a runtime or readiness verifier. Do not appoint the implementation author as its own verifier. A single PR still needs an independent verdict through this compatible verification route; do not substitute the author's assertion.

   Every assignment names repository, exact parent/base SHA, head SHA, PR URL, intent, relevant acceptance criteria, evidence locations, and read-only/no-publishing boundaries. Children do not inherit conversation history. Each exercises parent versus head through `skill://control-ui` or `skill://control-cli` when appropriate, in separate non-destructive workspaces with no tracked source edits. Do not run project-wide validation in competing editing tasks; this is a completed-change verification phase. Independent verification must not auto-apply competing implementations. Read `omp://tools/task.md` and `omp://task-agent-discovery.md` for available agents, isolation, plan-mode, depth and concurrency restrictions. Disclose unavailable tools or independence rather than manufacturing a pass.

   Each per-PR verifier returns `PASS`, `PASS+NOTES`, or `FAIL`, its identity, exact base/head, exercised scenarios, observed results, evidence, and remaining risks through `agent://<returned-id>`. The parent inspects full outputs and receipts before normalizing the per-PR verdict and any separate native patch/security findings into its ledger. Retain those native results in their own schemas; patch correctness alone never implies runtime `PASS` or coverage. Missing real-surface evidence is `FAIL` for readiness, with the missing prerequisite stated. Post the verdict on its own PR only if authorized; otherwise the parent retains the ready-to-post verdict and reports the publication boundary. A verdict's author must not have written the code. Do not assume a completed isolated verifier is resumable; its workspace is torn down. Use its saved output/history and assign a fresh verification with full context if needed.
2. **Land only the contiguous verified run rooted at the bottom.** Walk from the lowest unmerged PR and stop at the first without a passing verdict. Both `PASS` and `PASS+NOTES` pass, but explicitly discuss the notes before landing. A verified PR above an unverified PR is not landable. Report the highest verified contiguous PR number, or that the run is empty, and the exact gap that breaks the chain.
3. **Re-check that each verdict still describes the patch.** Record verdict head SHA, base SHA and the stable patch ID from `git diff <base-sha> <head-sha> | git patch-id --stable` in the parent's scoped trail. Keep evidence for binary or other changes a text patch ID cannot adequately represent; compare those artifacts directly. A rebase or base retarget may invalidate a verdict even when checks remain green. Before landing, compare against the current base-to-head patch ID. If the patch changed, re-verify. If identical, retain the code verdict but refresh mergeability and CI for the current head. Matching commit messages and green checks on old SHAs are not substitutes. A materially changed parent contract also requires re-verification of the inherited behavior even if a textual diff remains identical.
4. **Prepare only the bottom PR.** Fetch current trunk. With authorization and without disturbing unrelated work, rebase the lowest verified branch onto that exact tip when needed, push it, and retarget only that PR to trunk. On GitHub use `gh pr edit <pr> --base <trunk>`; use the selected forge's documented equivalent otherwise. Re-run step 3 after the push. Do not retarget, arm or merge descendants yet. If a published rebase needs authorization you do not have, report that prerequisite instead of forcing it.
5. **Land one PR at a time.** If the bottom is mergeable now and authorized, squash with `gh pr merge <pr> --squash --match-head-commit <verified-current-head-sha>`. If requirements are still running and the user requested merge-when-ready, arm only that PR with the same command plus `--auto`. Use the selected forge's documented squash/merge-when-ready equivalent otherwise. GitHub auto-merge and another forge's merge-when-ready are distinct states. A repository-enforced GitHub queue may enqueue rather than immediately merge; observe actual state. Never use administrator bypass to manufacture readiness. Wait for this PR to merge before preparing the next.
6. **Do not read `autoMergeRequest` as stack readiness.** It indicates at most that GitHub auto-merge was requested for one PR. It does not prove another forge's merge-when-ready is armed, a descendant is queued, the patch verdict is current, or the contiguous stack is safe. Confirm the selected forge's state for the current bottom PR. If it cannot report that state, say unknown. Do not arm another PR to compensate.
7. **Recompute after every merge.** Fetch trunk and confirm the reported merge commit is present in trunk. Drop the merged PR from the active frozen list while retaining its record. Inspect the new bottom's base, head, checks and patch ID. A host may automatically retarget a child, but do not assume it did. Repeat steps 3 through 6 only for the new bottom. Independent work stays outside this chain and ships on its own.
8. **Watch the current frontier until it merges or fails. Do not mutate the queue around it.** Reuse the read-only native observation recipe in `skill://sky-mode/playbooks/babysit.md`, but use Shipping's stop conditions, not Babysit's merge-ready stop. Supervise `gh pr checks <pr> --repo <owner>/<repo> --watch --interval 60` with `hub` start when checks are pending, observe logs/exit with bounded waits, and refresh the PR state after each wake. If checks finish while the merge remains pending, stop using the completed check watch and continue bounded parent status polling. Keep one observation owner and respect rate limits. No custom watcher or persistent scheduler is needed.

   Poll `gh pr view <pr> --repo <owner>/<repo> --json state,mergedAt,mergeCommit,mergeStateStatus,statusCheckRollup,autoMergeRequest,headRefOid,baseRefOid` and separately read required checks and review blockers. A check-watch exit or “ready” report never means merged. Advance only after `mergedAt` is non-null or `state` is `MERGED`, then confirm trunk in step 7. For another forge, use its documented current-state and check-watch operations and re-read until merged or blocked.

   Hard-fail when the PR is `CLOSED` without a merge; when a required check concludes `FAILURE` or `CANCELLED` and blocks merge after auto-merge is no longer pending; or when `mergeStateStatus` is `UNSTABLE` or `DIRTY` with no auto-merge pending. `BLOCKED` while checks are pending or auto-merge is armed is not itself failure. An unknown arming state is not proof of either failure or safety. Diagnose the actual pending requirement. Do not adopt Babysit's “frontier merge-ready; waiting for merge queue” stop here. Report each merge and updated ceiling. Answer user questions during the watch. An explicit stop, exhausted runtime capability or inaccessible forge state requires an honest checkpoint rather than a claim that background work will continue indefinitely. If the queue stalls, diagnose before mutation.
9. **Stop at the ceiling.** Once the verified run has merged, report what landed, the next unverified PR, and what verifying it requires. Extending the run starts a new pass through step 1. Stop owned check watchers. Do not clean up branches, worktrees or queues beyond the user's authorization.

**Reply:** the verified run and ceiling, every PR's verdict and independent author, what was armed and how its state was confirmed, what actually landed, and what the next gap needs. Link actual PRs and evidence rather than passing through unverified child summaries.

Command evidence is the GitHub CLI [view](https://cli.github.com/manual/gh_pr_view), [checks](https://cli.github.com/manual/gh_pr_checks), [edit](https://cli.github.com/manual/gh_pr_edit), and [merge](https://cli.github.com/manual/gh_pr_merge) manuals. Native process lifecycle and bounded waits are documented in `omp://tools/hub.md`. Saved output is not a live worker handle; session persistence is documented in `omp://session.md`.
