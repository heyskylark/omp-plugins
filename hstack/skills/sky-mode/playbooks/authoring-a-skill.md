### Authoring or modifying a skill

**You own the skill's voice.**

The parent copies these ordered steps into its todo before task-specific items. Keep an omitted step with `skip: <reason>`. Read and apply each named skill. A user pause on validation includes structural checks, runtime sessions, evals, and delegated checks. Do permitted authoring and clearly record deferred gates instead of bypassing the pause.

1. Read and apply `skill://create-skill` for authoring `SKILL.md` files. Use the flat native project layout `.omp/skills/<name>/SKILL.md`. Do not nest a skill below a taxonomy directory and assume discovery is recursive. Each skill has a directory-matching `name`, a concrete `description`, and `disable-model-invocation: true` for explicit invocation. Use only supported skill frontmatter. A skill is passive instructions, not an executable mode, event hook, agent definition, or custom tool.
2. Validate the skill when checks are permitted. Check that frontmatter has `name` and `description`, the name matches the directory, referenced files exist, and cross-skill links resolve to the intended dependency. Use exact `skill://<name>` links for reading and applying another skill, and `skill://<owner>/<relative-path>` for that owner's assets. Do not use traversal or rely on a fallback search. Check that all command examples name real available tools and documented arguments, and that every runtime helper exists or has been replaced by complete native instructions. Inspect discovery collisions rather than assuming the file you authored wins. `disable-model-invocation` hides automatic model exposure but does not make an installed skill inaccessible by its exact URI or enabled interactive skill command.
3. Use test cases for structural behavior, not subjective prose. A structural case must defend an observable contract, boundary, transition, or failure that a plausible broken skill would get wrong. Read and apply `skill://sky-mode/playbooks/eval.md` when evaluating whether instructions change agent behavior. Hold inputs and comparison criteria constant and distinguish observed behavior from a static review. Skip subjective voice-only cases with a reason instead of inventing assertions that pin wording. Do not launch OMP sessions, eval agents, or tests while the user has paused runtime validation. Report what was and was not checked.
4. Read and apply `skill://sky-mode/playbooks/opening-a-pr.md` when the requested repository workflow includes a PR. Otherwise retain this step with its skip reason. Skill authoring does not grant authorization to commit, push, publish, or merge.

When in doubt, delete. Keep only prose that changes a decision. Tell the agent to do the thing and omit the rationale unless the rule would otherwise be confusing. Match tone to scope. Read and apply `skill://principle-encode-lessons-in-structure`; point at structural sources such as types, existing READMEs, and configuration rather than duplicating them. Delegate to other skills by exact path. Do not restate their workflow. A recurring workflow with no existing owner earns a proposed new skill, not a second copy hidden inside another skill. Read and apply `skill://unslop` for the prose surface.

Keep the parent responsible for voice and integration. Scope inline first. For genuinely independent substantial skills or asset sets, use one native `task` batch with explicit isolated file ownership and shared format contracts. Choose configured general task agents for authoring judgment and independent workflow review, and `sonic` for mechanical transformations. Use the bundled `reviewer` only for a compatible patch-bug review with its native findings output, not a custom skill-quality rubric. Every child gets source pointers, required dependency paths, acceptance criteria, and an instruction to skip tests, builds, linters, formatters, and runtime validation until integration. Children have no parent conversation and do not own todos. Consume `agent://<id>` outputs, keep a scoped parent-owned `local://` notepad, and use known `hub` IDs for follow-up. Do not create a special runtime agent type merely to write a skill, and honor available spawn and isolation limits.

**Reply:** a summary of the skill, key design decisions, and validation notes. Name dependency or tool availability problems and paused checks explicitly. Do not call an unexecuted behavioral check successful.
