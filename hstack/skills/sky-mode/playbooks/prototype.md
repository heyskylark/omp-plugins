### Prototype

**You own the design decision, not the code. The prototype is a throwaway instrument. The real build follows Feature.**

This is the playbook where production polish and the usual smallest-diff preference give way to a cheap decision. Speed over polish. Avoid a production implementation plan, tests, and abstractions. The rigor is in choosing the right experiment and observing it. Propose useful variations the user did not ask for, throw an approach away, and try another.

The parent copies these ordered steps into its todo, not a second production plan. Keep skipped steps with `skip: <reason>`. Read and apply named skill dependencies. A runtime-validation pause includes prototype execution, browser inspection, timing runs, and delegated experiments. You may prepare an authorized sketch, but report the empirical decision as unresolved until observation is allowed.

1. Scope the decision the prototype exists to make. Name the layout, interaction, density, behavior, timing, or approach under question. No decision means no prototype. Read and apply `skill://sky-mode/playbooks/feature.md` instead. Do not ask the user to settle a fact an authorized experiment can observe; reserve questions for genuine product or preference choices.
2. Gather references when the design space is open. Search for prior art and summarize a moodboard of themes, palettes, and layouts. Let the user pick subjective directions before building. Skip this step when the direction is already set. Use `read` for known static references and the available design tools when the requested design surface calls for them. A read-only investigation seeking a cited answer stays an investigation rather than becoming an unsolicited sketch.
3. Build throwaway in an isolated scratch directory outside production source. For a visual decision, use vanilla HTML/CSS/JS or the lightest stack that renders the idea, with CDN dependencies only where permitted. Prefer a development server with hot reload when already available. Start it through native `hub` with a stable name and explicit readiness, inspect logs, use send for interaction, and stop the owned process when finished. Do not install packages or expose a service externally without authorization. For a behavioral or timing decision, use the smallest script exercising the question. No production framework unless it is essential to the measured behavior, no permanent tests, and no abstractions.

   Keep simple sketches inline. If several substantial independent alternatives warrant agents, scope them first and dispatch one batch with disjoint scratch ownership, shared comparison conditions, and no mid-flight validation. Select configured general task agents for implementation and design judgment, and `scout` for substantial independent research. A design judge must support the comparison's scope and output contract, not the bundled `reviewer`'s patch-only findings. The parent owns the todo, decision, scoped `local://` notepad, and final observation. Use `agent://<id>` outputs and known `hub` IDs. Honor isolation, spawn, and plan-mode limits. Do not allow native auto-applied competing patches into production; use isolated no-apply alternatives as prescribed by `skill://arena` when needed, or return read-only proposed artifacts.
4. Compare alternatives behind one switcher, such as buttons or a keypress, and label each variant. Read and apply `skill://principle-exhaust-the-design-space`. Keep the same data, viewport, inputs, and measurement conditions so differences inform the decision rather than reflect setup drift.
5. Verify on the matching surface when execution is allowed. Read and apply `skill://control-ui` for visual browser or Electron work and `skill://control-cli` for CLI or TUI behavior. Open a named Eval `browser` tab, observe the rendered surface, screenshot each visual variant, and drive its interaction. Re-observe after re-rendering before using element handles. Use a dedicated target for authenticated or attached sessions and respect the user's external-action authorization. For behavior or timing, observe the thing being decided by logging timing, printing output, or watching the render. The observation is the test here, not an assertion or a production test suite. Report unavailable or inconclusive evidence rather than substituting compilation. Close owned browser handles when finished.
6. Present alternatives, tradeoffs, and a recommendation. The deliverable is the decision plus the throwaway artifact, not shippable code. Hand the chosen direction to `skill://sky-mode/playbooks/feature.md`, or read and apply `skill://architect` when the next decision is structural. Do not silently promote the scratch implementation into production. Keep or remove the artifact according to the user's request and ownership; never delete unrelated work. A PR is not a prototype requirement. Use `skill://sky-mode/playbooks/opening-a-pr.md` only if the requested repository workflow explicitly calls for one.

**Reply:** the variants explored, screenshots for a visual decision or actual observed output/timing for a behavioral one, tradeoffs, your recommendation, and the scratch path. Say plainly that the prototype is throwaway. If observation is paused, name the prepared variants and the deferred decision rather than claiming a winning experiment.
