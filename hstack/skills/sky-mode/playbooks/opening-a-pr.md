### Opening a PR

Invoked at the end of implementation playbooks to prepare delivery. Preparing does not grant authority to commit, push, publish, or merge. Follow the user's instructions and repository policy. Without publishing authorization, return the prepared title/body and exact local state instead of opening a PR.

**Worktree.** Work in a dedicated git worktree from the repository's trunk, normally main. Inspect the actual branch, base and existing changes first. Children do not magically get a different worktree. Independent editing tasks use native `task` isolation when available and allowed; shared parent mutations have one integration owner. Read `omp://tools/task.md` before choosing isolation, since successful work can auto-apply and isolated workspaces are cleaned at completion. Pass each child its scope and base facts explicitly. Preserve unrelated dirty work in its original location and transfer only task-owned changes to a fresh worktree when necessary. Do not hard-reset a dirty or snarled worktree, destroy another actor's edits, or replace the entire branch merely to simplify this task. Recover from known branch and patch facts non-destructively.

**Commits.** Within commit authorization, checkpoint meaningful changes liberally. Before opening PRs, arrange small ordered landable commits that tell the story. Amend a just-made private commit when the fix belongs to it; use a new commit for separable work. Rewriting published history or force-pushing requires explicit authorization and coordination. Each commit should be suitable as a future narrow PR.

**PRs.** Read and apply `skill://deslop` over the diff before committing. Read and apply `skill://no-comments` before review. Write every PR title, description and commit body with `skill://technical-writing`, then `skill://unslop`. Apply every technical-writing layer except Diátaxis. Use one word for each action, keep articles, and prefer a plain verb over an unnecessary `-ing` form.

**Titles.** Use Conventional Commits in the form `type(scope): subject`. Types are `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf`. Use the actual changed area as scope, such as `hstack` or `sky-mode`. Keep the subject short and imperative. Name a real symbol when it carries the change. For example, `fix(sky-mode): retarget opening-a-pr babysit trigger`. No trailing period.

**Descriptions.** The body briefs a reviewer who already has the diff. Explain why the change exists, what is out of scope, and how it was proved. The squash commit body is the PR body. If it would exceed about 40 lines, cut it rather than attaching the lab notebook.

Use these sections in order and drop empty sections.

- `## Why`. Intent and approach in one or two short paragraphs. No SHAs, rebase genealogy, or “based on main” preamble.
- `## Scope`. Bullets with real symbols and paths. Name both sides of a rename or retarget. State in/out boundaries only when they matter. No file-by-file essay.
- `## Tradeoffs`. Rejected alternatives that a reviewer would otherwise ask about. Omit when there was no real choice.
- `## Blast Radius`. One to three sentences naming who or what is touched and why the change is safe or risky. State the continuing cost if trunk remains red without the fix.
- `## Verification`. Each real run path and outcome. For performance, one primary number with units in `before → after` form. Link the produced arena or swarm evidence artifact for remaining details. No sample-size methodology, lane recitals or metric tables in the briefing.

Attach screenshots or video after these sections when they prove a claim. Keep full SHAs, detailed review verdicts, experiment methodology, lane inventories, tooling corrections and file checklists in a linked artifact. Local artifact links are useful to the parent but not necessarily accessible to PR reviewers; publish evidence only with authorization, or state its local path and availability honestly. Do not fabricate an externally accessible link. Do not use `## Summary` or `## Test plan` boilerplate. A commit body does not repeat its subject.

**Forge.** Resolve once before the first PR operation and keep that choice for create, edit, view, watch and merge. `gh` is the default. Prefer installed Origin only if it resolves the repository and its documented interface is available; consult its installed help before using it. Otherwise remain on `gh` and record why. Do not require Graphite. Read the [create](https://cli.github.com/manual/gh_pr_create), [edit](https://cli.github.com/manual/gh_pr_edit) and [view](https://cli.github.com/manual/gh_pr_view) references for the installed command version before relying on flags.

**Size and stacks.** Prefer five narrow PRs to one oversized PR. A stack is a base-branch chain. Its root targets trunk; each child rebases onto its parent's exact tip and targets that parent branch. Independent work branches from trunk. Before substantial stack work, reconcile the intended base with current trunk within the owner's authorization. This topology work belongs here or to Shipping, never to Babysit. On GitHub create a child with `gh pr create --base <parent-branch> --head <child-branch> --title <title> --body-file <body-file>` and retarget with `gh pr edit <pr> --base <parent-branch>`. Supply the repository explicitly when cwd does not uniquely identify it. Explicit `--head` avoids create's implicit fork/push prompt; push separately only when authorized. Origin uses its documented create/edit equivalents with an explicit parent base.

**Readiness.** Open ready for review, not draft, once the work and repository requirements permit publication. For `gh`, omit `--draft`; for another selected forge explicitly choose its documented open/ready state. Do not promote an existing user-owned draft contrary to instructions. If an authorized creation unexpectedly yields a draft, use the forge's documented ready operation and re-read it. Run `gh pr view <pr>` or the selected forge's view before referring to status. A create command can partially succeed, for example after attachment failures; inspect its actual output and existing PR before retrying to avoid duplicates. Even a create dry run may push, so it is not a safe substitute for local preparation.

**Babysit.** Opening never starts a babysit. Post the URL and continue building. Finish the phase or stack first. Run `skill://sky-mode/playbooks/babysit.md` only when the user requests a separate status or babysit pass. Babysitting each newly opened PR stalls construction and repeats checks invalidated by later waves. Push back when feedback drifts from intent.

A child entrusted to open a PR reads and applies `skill://interrogate`, `skill://deslop`, and `skill://no-comments` within its delegated scope and available capabilities. It returns the actual URL, base/head identities, evidence, and unresolved limitations through its `agent://` result. It does not babysit. The parent reviews the result and owns the user-facing summary. A child unable to publish or invoke a required gate returns that boundary to the parent rather than silently skipping it.
