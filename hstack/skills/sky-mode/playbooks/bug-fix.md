### Bug fix

**You own this task. Plan, review, verify.** Keep investigation, implementation, and review accountable to one lead. Delegate substantial independent work when the active policy permits it.

Be scientific. Every shipped line traces to evidence of the failing mechanism. Belt-and-suspenders code that might help is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, remove the changes it motivated without touching unrelated work. Ship the smallest change the evidence justifies.

Accept user-reported failures as ground truth. Reproduction establishes a regression instrument and before/after evidence; it is not a demand that the user prove the report. The parent copies the ordered steps into its todo before task-specific items, retaining omissions with `skip: <reason>`. Read and apply each named skill. A user pause on runtime validation overrides every execution gate below, including delegated repros and instrumentation. Preserve the report, finish permitted investigation and edits, and state exactly what remains unverified.

1. Establish the reproduction yourself on the matching surface. Read and apply `skill://control-ui` for browser or Electron work and `skill://control-cli` for CLI or TUI work. Do not hand the repro to the user merely because a debugging protocol suggests asking them. Drive the instrumented runtime yourself. Open a named Eval `browser` tab before web interaction, observe the target, exercise the failing action, and capture the actual result. Start supervised programs with native `hub` start and observe readiness; use logs and send for output and interaction, and stop only your owned process when finished. Respect authorization for logged-in sessions and external actions.

   Ask the user to supply a runtime step only after reaching the tool's real boundary and stating the specific reason it cannot reach the target. When a direct repro does not trigger, synthesize the reported trigger safely, tighten conditions, or instrument the path until the mechanism becomes observable. Do not dismiss the report if the environment differs. Do not use destructive data changes, new installations, or forbidden runtime work to force a repro. State missing access or a paused gate instead.
2. Binary-search the cause. Form candidate hypotheses and rule them out until one survives. Read and apply `skill://how` for the affected subsystem and `skill://why` for regression history. After inline scoping, these are independent research slices and may run in one native `task` batch with `scout` agents when the delegation gate is met. Give the exact skill paths, affected scope, report, and evidence pointers; children do not inherit conversation. Do not ask them to recursively invoke an orchestrator or maintain their own todos.

   Each pass chooses the split that removes the most remaining problem space, gathers permitted runtime evidence, and eliminates hypotheses. Use the native debugger for breakpoints, stepping, stacks, scopes, and variables when program state is unclear. Add narrow temporary instrumentation or logging only when needed, and read it while the code runs. Do not guess. For a long or stubborn hunt, continue a parent-owned hypothesis/evidence cycle using the todo and a scoped `local://` notepad. Native `hub` supervises the program; it is not a custom scheduler. Record the next experiment and stopping condition, honor cancellation and tool/spawn limits, and do not claim an unbounded background loop. Confirm the surviving mechanism before the step-3 design or adversarial fan-out.
3. Plan the fix. Read and apply `skill://principle-fix-root-causes`. If the fix crosses a function boundary, read and apply `skill://architect` first. If the design remains contested, read and apply `skill://interrogate` before shipping. Map semantic changes with LSP definitions and references before edits; preview applicable rename or code actions and use `ast_edit` for structural rewrites rather than blind replacement.

   Keep exact path ownership. Delegate substantial independent implementation slices to configured general task agents in isolated native tasks, with the confirmed mechanism, source pointers, intended data shape, and observable acceptance criteria. Use `sonic` only for fully mechanical edits. Shared batch context has `# Goal`, `# Constraints`, and `# Contract`; assignments have `# Target`, `# Change`, and `# Acceptance`. Every editing child skips tests, builds, lint, formatting, and runtime checks until the lead integrates the work. No hardcoded models. If a fix is small, inseparable, or spawning is prohibited, implement inline and disclose any unavailable review separation instead of bypassing limits. Read `agent://<id>` outputs and review the actual diff. Use known `hub` IDs for follow-up; isolated completed workers need a new scoped handoff rather than assumed revival.
4. Verify on the same surface. The original repro now passes. Inconclusive or wrong-surface evidence is not a pass; flag it. Unit tests can show branch behavior but do not alone establish absence of the reported runtime bug. The lead owns the before/after evidence. When runtime validation is paused, label this gate deferred, not successful.
5. Stage delivery so the failing repro precedes the fix in history when commits are authorized. Read and apply `skill://tdd` for a cheap local failing-test-first path. Skip that cadence with a reason when the test would be expensive, integration-heavy, or unclear; retain the actual runtime reproduction as evidence. Read and apply `skill://principle-sequence-verifiable-units`. A failing regression test first and the fix above it tell the causal story. Keep a permanent regression only when it guards observable behavior against a plausible recurrence. Do not commit, rebase, or push outside the user's authorization.
6. If the requested repository workflow includes a PR, read and apply `skill://sky-mode/playbooks/opening-a-pr.md`. Otherwise keep this step with its skip reason. Opening a PR does not implicitly authorize merge or babysitting.

If a run was blocked, paused, or could not reproduce in the available environment, say so instead of inventing output or claiming the bug absent. Separate the user's report from observations made in this run.
