### Perf issue

**You own the measurement story. Plan, review, verify the numbers.** Tie every fix to a measurement. Reading source does not replace measuring the real system.

1. **Capture a baseline trace on the matching surface.** Read and apply `skill://control-cli` for CLI or TUI work, or `skill://control-ui` for browser or Electron work. Reproduce the relevant workload and capture its actual trace or profile. Record the revision, command or interaction, input size and state, environment, sampling interval, unit, and artifact path. Use repeated measurements when variability could hide the result. Manage owned services through `hub` start with observed readiness, logs, send, and stop. For live process state use the OMP debugger through `xd://debug`, not shell guesses. A trace from the wrong process or interaction is not a baseline for this complaint.
2. **Ground hypotheses.** Read and apply `skill://how`. Do not claim a performance ceiling without running the workload first. Eight strategy families generate hypotheses, not a checklist. A family earns an attempt only when the trace shows its signal.
   - **Elimination.** Before optimizing the hot path, ask whether it needs to exist. Look for a computation nobody consumes, a feature gate always off for this user, a sync redundantly mirroring state, or a legacy path retained just in case. The trace shows what is slow, not what is deletable. Establish semantic necessity through the how pass rather than the profiler.
   - **Divide and conquer.** The dominant cost scales with input size. Split work so each piece touches less through chunking, sharding, or pruning the search space, or so independent pieces can run in parallel.
   - **Caching.** The same computation or fetch repeats on identical inputs. Store and reuse the result. Name what invalidates it before claiming the win. Account for memory, freshness, and cold versus warm behavior.
   - **Indirection.** A cheaper intermediate can absorb expensive hot-path work. Use an index instead of a scan, a queue to move work off an interactive thread, or a handle that permits a cheaper implementation. Add the hop only when it removes more from the critical path than it adds.
   - **Batching.** Many small operations each pay a fixed overhead, such as an RPC, query, syscall, or draw call. Coalesce them so the overhead is paid once per batch. Check any latency or ordering cost.
   - **Redundancy.** One slow instance or attempt dominates the wait. Replicas, hedged requests, or speculative execution can duplicate work and take the fastest result. The trace must show waiting dominates and the system has headroom. Account for total resource cost and duplicate side effects before using this family.
   - **Lazy evaluation.** Cost lands on results never used or not needed yet, such as eager boot initialization or offscreen rendering. Defer work until first use and measure whether the cost merely moved to another user-visible wait.
   - **Scheduling.** Work must happen but not during the interactive moment. Move it to idle callbacks, background warmup after boot, precomputation before arrival, or cleanup after the frame commits. Measure interactive latency rather than claiming total work fell.
3. **Plan and implement from the trace.** If the fix crosses a function boundary, read and apply `skill://architect` first. Delegate substantial implementation to the configured general task agent with a bounded hypothesis, owned paths, and evidence pointers. Use `sonic` only for a mechanical change. Keep trivial work inline. Review the diff yourself. Read and apply `skill://principle-sequence-verifiable-units`. Verify each attempt before trying the next. Keep shared validation with the parent after concurrent edits settle. Capture a post-fix trace from the same surface, workload, and measurement regime, and run the relevant correctness gate. Never retain a speedup that breaks required behavior.
4. **Parse and compare the artifacts.** Use Eval to reduce actual JSON or other profiling output, SQLite for suitable structured captures, and diffs of comparable observations. Preserve raw captures and link reductions back to them. Compare baseline and post-fix numbers with units and a stated delta convention. Account for noise and tradeoffs. Inconclusive evidence or a wrong-surface capture is not a pass. Flag it, repair the measurement when possible, and retain uncertainty if it cannot be resolved. Never fabricate a trace, benchmark number, or test script result.
5. **Cite the measurement in the delivery.** Include the primary before and after number and link the actual evidence artifacts. Local artifacts are not automatically accessible to a remote PR reviewer. Publish only authorized, appropriately redacted evidence or provide an honest local reproduction path. Do not expose private process data or session material.
6. **Open a PR only when authorized.** Read and apply `skill://sky-mode/playbooks/opening-a-pr.md` when PR creation, commits, and required pushes are within the user's authorization. Otherwise return the local fix and measurements without external writes.

For sustained improvement against a target rather than a one-off fix, read `skill://sky-mode/playbooks/hillclimb.md`.

**Reply.** Baseline number, post-fix number, delta, and actual artifact path. Include units, meaningful resource or correctness tradeoffs, and any inconclusive or incomplete outcome instead of presenting it as a win.
