### Eval

**You own the experiment design. Plan, blind, run, synthesize.** Use this to measure how a skill, structure, or prompt variant changes agent behavior before promoting it.

**Non-negotiables for blinding.**

- No `eval`, `test`, `judge`, `experiment`, `rubric`, `score`, `compare`, `benchmark`, `candidate`, or `arena` in any directory, file, or prompt you supply to the candidate. Audit task-visible workspace names, agent labels, shared context, artifact names, and injected instructions for leakage before launch. If ambient harness metadata cannot be blinded, disclose that limitation rather than claiming a fully blinded run.
- The candidate prompt looks like an organic user request. State the goal, not the meta.
- No chain-eliciting cues. Do not ask which skills, principles, or files it applied. Ask for design notes generally. Grade behavior from tool evidence and code shape, not self-report or private reasoning.
- Use sanitized, project-shaped directory and slug names a user might choose. Do not tell candidates other candidates exist.
- The judge may know it is judging, but sees outputs by sanitized labels only, never model names or identifying launch metadata.
- For two variants, one judge scores both sets in one pass against one scale, blind to which set each came from.

**Steps.**

1. **Frame.** State the variant and the behavior that counts as success. Write three to six concrete criteria for the judge only. Hold the rubric, variant mapping, and launch ledger in parent-owned local artifacts outside task-visible inputs. Fix the task, input data, available tools, and stopping constraints across variants. Record unavoidable differences and what conclusions they prevent.
2. **Set up sanitized environments.** Give each attempt its own workspace with its variant installed. Plant only context an organic task would have, such as the same project skeleton and naturally discoverable skills. Children do not inherit the conversation, but do receive workspace context and discovered skills and share the parent's `local://` root. That root is not a secrecy boundary. Do not pass private rubric paths or expose a common workspace containing other attempts. Audit what the child actually receives. If the available launch surface cannot provide equivalent isolated inputs, mark the limitation and do not invent isolation.
3. **Author one organic prompt.** Write what a user would type, without measurement leakage. Ask for the artifact and ordinary design notes, including considered and rejected alternatives. Supply identical text to every attempt except the necessary sanitized workspace pointer.
4. **Launch N parallel attempts.** Read and apply `skill://arena`, Phase B, subject to this playbook's stricter blinding rules. Use configured general task agents for reasoning and implementation. Optional configured agent definitions may supply distinct model families. Select agent types, never pass a model to `task`. If only one family is available, report repeated same-model runs rather than claiming model diversity. Launch genuine independent attempts together within spawn, concurrency, isolation, and plan-mode limits. Keep every result separate. Ordinary isolated `task` work can auto-apply, so use the documented Eval `agent()` controls `isolated: true, apply: false, merge: false` for competing code attempts when available. If isolation controls are unavailable, use non-editing proposed artifacts with separate sanitized output paths and report the reduced experiment fidelity. Never apply every competing patch. The parent owns phase tracking; children produce outputs, not child plans or recursive orchestration. Record actual agent IDs and returned `agent://` output handles privately. Record failed or incomplete attempts as dropouts and continue with N minus the dropouts when the remaining evidence can answer the question.
5. **Launch one blinded judge.** After every attempt has settled and its output is frozen, apply `skill://arena`, Phase C. Use the configured general task agent, or an existing specialist whose role and output contract support rubric scoring, preferably from a different model family. The bundled patch-only `reviewer` cannot supply this scoring contract. Strip identity-bearing headers, paths, and metadata from copies provided to the judge without altering substantive output. Provide the rubric and sanitized labels, not the launch ledger. Ask for criterion-by-criterion scores and a reasoned verdict on one scale. Disclose a same-family judge limitation. The parent reads the outputs while the judge works.
6. **Verify the observable chain.** Read only `history://<id>` for the known task IDs created for this run. Use actual tool calls and results to establish which files were opened and what actions occurred. Correlate those observations with the resulting code. Read bounded relevant transcript sections, not full private session dumps. Never search unrelated session directories or publish private reasoning. History is a concise view, and persisted content may be truncated or unavailable. Mark missing evidence as unknown, not as proof a step happened or did not happen. A candidate's account of its own behavior is not evidence.
7. **Read every output end to end and synthesize.** Compare your criterion-by-criterion assessment with the judge's verdict. Disagreement can expose bias or an ambiguous rubric. Resolve it from artifacts, or preserve the uncertainty and recommend a more discriminating follow-up. Promote only what the observations support. Do not relabel an incomplete, contaminated, or inconclusive run as a win.

**Reply.** Variant under test, rubric, per-candidate notes under sanitized labels, judge's verdict, your synthesis, and a recommendation on promotion. Include actual artifact pointers, dropouts, blinding or model-diversity limitations, and unknowns that materially constrain the recommendation. Keep the identity mapping and private session material out of the public report.
