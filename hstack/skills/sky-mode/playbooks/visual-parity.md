# Visual parity

**You own pixel-exact equivalence. The baseline is the spec. You do not touch it.** Equivalence is verified by image diff, not by eye.

1. **Establish the baseline before any migration.** Use a visual regression harness that screenshots the current component across its states, plus the target when matching two implementations. Inventory the components and state matrix, including applicable default, loading, empty, error, disabled, focus, hover, selected, expanded, responsive, and theme states. Capture the baseline from the unchanged implementation and record its revision and harness location. Fix the comparison controls before capture: browser/runtime version, OS/rendering surface, viewport, device scale, fonts and font readiness, locale, timezone, theme, data, scroll position, animation/time state, and capture boundaries. Give baseline and treatment identical controls. Establish repeatable baseline captures before migration; if the unchanged baseline cannot reproduce itself, stop and resolve that prerequisite without altering the accepted images. No baseline means no parity claim. This is blocking, not a follow-up.
2. **State and hold the anti-shortcut clauses.** No harness modifications, baseline tampering, or component restructuring merely to make a diff pass. Do not regenerate accepted snapshots, add masks, weaken thresholds, crop away failures, remove states, or substitute an easier surface to manufacture zero. If the baseline looks wrong, stop and ask for a product decision rather than editing it. A genuinely requested new baseline is a separate explicitly approved contract, never an unreported migration change. Keep baseline assets and the comparison contract outside delegates' write scope.
3. **Migrate one component at a time.** Read and apply `skill://principle-separate-before-serializing-shared-state`. Shared primitives migrate first as a blocking phase, with their affected states compared before dependents proceed. Then parallelize genuinely independent components across isolated workspaces with one owner per component. Scope inline first and send one native `task` batch with shared `# Goal`, `# Constraints`, and `# Contract`, plus per-item `# Target`, `# Change`, and `# Acceptance`. Choose the configured general task agent for implementation and `sonic` only for strictly mechanical work. Give each owner exact baseline/harness pointers, component files, state matrix, and no-touch fences. The parent owns the ledger and integration. Children do not recursively orchestrate or run project-wide validation mid-flight. If shared state cannot be eliminated, serialize that specific boundary. Native isolated tasks may automatically apply their patches; these are complementary component changes, not competing implementations to apply all at once. Record capacity or isolation limits and reduce the concurrent wave honestly when required.
4. **Compare every component on the matching surface.** Read and apply `skill://control-ui` for web/Electron/browser surfaces or `skill://control-cli` for terminal surfaces. For web, start needed baseline/treatment servers under separate `hub` process names with explicit cwd, ports, and observed readiness. Open dedicated named tabs with the Eval browser prelude, set equal viewports, observe and exercise the same state recipe, wait for the defined stable state, and capture both sides. Use direct helpers for normal actions and `tab.run` for custom browser execution. `tab.screenshot()` returns an artifact path and does not accept an output filename; record the returned path. Do not navigate an unrelated visible or authenticated user tab. For other surfaces, use the matching supported runtime control/capture mechanism and disclose when none is available.

   Run the frozen harness's image comparison for each state at matching dimensions. Preserve baseline, treatment, and diff images plus the exact comparator result. A nonzero pixel diff is a failure. Inspect the delta to identify the styling, geometry, font, asset, state, or environment mismatch, fix the treatment, and recapture the same state. Repeat the native inspect/change/compare cycle per component until every required diff is zero. Never use visual resemblance alone as proof. Infrastructure failure, missing screenshots, unavailable fonts/runtime, or an incomplete matrix is blocked/unverified, not a pass. Honor tool and execution limits; report the remaining failed states if a real limit prevents convergence.
5. **Deliver per component or safe batch.** After independent work is integrated, the parent runs the frozen matrix against the integrated treatment so shared changes cannot invalidate earlier evidence unnoticed. Read and apply `skill://sky-mode/playbooks/opening-a-pr.md` per component or safe batch. Commits, pushes, and PR creation remain subject to user authorization; a parity task does not silently grant it. Close owned browser tabs and stop only owned servers when evidence collection is complete. Keep the immutable baseline and report artifacts needed to reproduce the comparison.

## Parity ledger

Keep one row per component and required state. Record owner, baseline revision/image, treatment revision/image, surface and controls, harness/comparator invocation, diff image, differing pixel count, verdict (`zero`, `nonzero`, or `unverified`), and the next action. Record shared-primitive prerequisites and missing states explicitly. A component passes only when all its required rows have a zero diff under the unchanged comparison contract.

## Reply

- Components migrated and the image-diff result for each, including every failed or unverified state.
- Baseline revision, immutable baseline harness location, and comparison controls.
- Treatment and diff artifact paths actually produced, with integrated-matrix results.
- What remains, why it is blocked or failing, and any authorization needed for delivery.
