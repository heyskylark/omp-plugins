### Refactoring

**You own the contract. The structure changes. The behavior does not.** Feature adds behavior. Bug fix corrects it.

If cleanup reveals a missing feature or a real bug, split it out and deliver the structural change first against the pinned contract. A redesign is allowed, but name the behavior change and read `skill://sky-mode/playbooks/feature.md`. Large or cross-cutting structural work routes to `skill://figure-it-out`. This playbook owns focused-to-medium changes.

The parent copies these ordered steps into its todo before task-specific items. Keep skipped steps with `skip: <reason>`. Read and apply the named skills before using them. If the user pauses runtime validation, do not run a baseline, equivalence check, test, or smoke exercise through another agent. Record the blocked evidence gate. Do not label unverified behavior preservation as proven.

1. Pin the behavior contract first. Read and apply `skill://how` over the affected subsystem. Before structure moves, write a characterization test, snapshot, or equivalence harness that captures current behavior. If the area has no coverage, write the pin first. Type checking and lint are not a pin. Prefer a temporary equivalence harness where a permanent test would only enshrine implementation details. Under a validation pause, preserve the intended baseline procedure and identify the unexecuted pin before proceeding with any permitted edits.
2. Name the structure the code is missing. Read and apply `skill://principle-model-the-domain`. Boring code stays when its shape is already clear and local. The reshape must delete branches or invalid states, not add indirection.
3. Name the target shape. State the module layout, types, and call graph the subsystem would have if built today. Read and apply `skill://principle-foundational-thinking` and `skill://principle-redesign-from-first-principles`. If the target crosses a function boundary, read and apply `skill://architect` for parallel design exploration before moving it.
4. Subtract before adding. Read and apply `skill://principle-subtract-before-you-add`. Delete dead code, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape. Read and apply `skill://principle-laziness-protocol`. Keep the smallest change reaching the target. Remove only your speculative changes that do not earn their place; never discard unrelated user work.
5. Move in small behavior-preserving steps, each keeping the pin green when execution is permitted. Read and apply `skill://principle-migrate-callers-then-delete-legacy-apis`. Migrate every caller and delete the old API in the same wave. No compatibility shims or parallel old-and-new paths.

   Before semantic edits, use LSP definitions, references, implementations, and relevant type information to map the symbol and its consumers. Preview LSP rename or rename-file actions with `apply: false`; inspect available code actions before selecting one to apply. Use `ast_edit` for syntax-aware codemods, inspect its staged proposal, then resolve or reject it. When the language server or action is unavailable, state the limitation and use a bounded structural search plus an explicit consumer census. Do not pretend text replacement has semantic coverage. Spot-check renames against actual files, including strings, prose, and back-references that a language server may miss.

   Keep one integration owner. After inline scoping, delegate only genuine substantial independent slices. Use a native `task` batch with disjoint path ownership and `isolated: true` when available. Choose `sonic` for fully mechanical edits and the configured general task agent when reasoning is required. Supply the names being moved, the pinned behavior, exact files, target shape, and success criteria. Shared context uses `# Goal`, `# Constraints`, and `# Contract`; each assignment uses `# Target`, `# Change`, and `# Acceptance`. Tell children to skip validation, builds, lint, tests, and formatters during edits. Do a small or inseparable change inline rather than inventing concurrency. Honor spawn, isolation, and plan-mode limits. The parent owns the todo and scoped `local://` notepad, reads `agent://<id>` results, and reviews the diff itself. Use known `hub` IDs for follow-up and known `history://<id>` sessions for transcript evidence.
6. Prove unchanged behavior on the real artifact, not merely compilation. Read and apply `skill://principle-prove-it-works`. For larger reshapes, diff old-versus-new outputs, replay a recorded baseline against the new code, or run a matching-surface smoke exercise. Read and apply `skill://control-ui` for browser or Electron surfaces and `skill://control-cli` for CLI or TUI surfaces. Browser proof uses an opened Eval `browser` tab and the real interaction; supervised runtimes use `hub` start, readiness, logs, send, and stop. Own verification yourself. A delegate's looks-good summary is not proof. Report inconclusive, wrong-surface, or paused checks explicitly.
7. Confirm the change is worth keeping. Read and apply `skill://principle-minimize-reader-load`. Name the reader-load reduction. If the diff does not lower reader load somewhere, discard your reshape instead of shipping motion for its own sake.
8. Shape small ordered commits when authorized. Subtraction first, then the reshape, then justified follow-on cleanup. Read and apply `skill://principle-sequence-verifiable-units` so each behavior-preserving slice stays green before the next. Do not rewrite shared history or commit without authorization. If the requested repository workflow includes a PR, read and apply `skill://sky-mode/playbooks/opening-a-pr.md`; otherwise retain the PR step with its skip reason and report the proposed delivery order.

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped, and what you reverted. State any unexecuted gate. No new behavior.
