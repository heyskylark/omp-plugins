### Orchestrate

**You own the program, never the code. Author briefs, drain the queue, keep the frontier green, decide.** Use for a project that outlives a single agent and needs many independently owned units across explicitly resumed sessions. A single task driven to a predicate uses `skill://sky-mode/playbooks/autonomous-run.md`. A bespoke ambitious run uses `skill://figure-it-out`. If one agent could finish inside the active session's limits, work directly with ordinary workers where useful, inline verification and authorized incremental delivery. Do not impose the registers and pilot machinery below.

Read and apply `skill://sky-mode`. Ceremony scales with the program. Completions are queue events, not interruptions. Every assignment and follow-up carries the current standing orders. The brief is the product. Children have no parent conversation and should not have to guess intent.

#### Roles and placement

- **Coordinator, this parent session.** Frames the program, authors briefs, drains results, owns todo and all shared records, makes judgments and reports to the operator. It does not author product code. Assign code changes, conflict resolution and restacks to scoped implementation tasks. Mechanical integration of an accepted patch or clean worker commit is parent bookkeeping, only within authorization. Integrate verified units continuously rather than waiting behind an idle integration owner. Native `task` or `eval agent` creates children, `hub` coordinates known IDs, and `read` retrieves `agent://` outputs. No custom worker fleet, scheduler, bootstrap, database or store-lock service.
- **Track lead, only when needed.** A bounded planning/review task can consolidate one independently scoped track when one parent drain cannot handle all reports. It returns a rollup, not a raw transcript dump. It does not recursively run this orchestrator, mutate parent todo or autonomously spawn its own tree. The parent dispatches its concrete worker/verifier briefs and retains every returned ID. Extra layers repay orientation cost; omit them for a track the parent can drain. Do not assume a fixed depth is allowed; obey actual spawn policy and `task.maxRecursionDepth`.
- **Worker and verifier.** Use the configured general task agent for reasoning, code, design critique, evidence judgment and executable verification with custom verdicts, `scout` for code/search research, and `sonic` only for mechanical edits. A discovered specialist must fit both the assignment and its tools/output contract. Bundled `reviewer` is only for patch-introduced bugs anchored to changed diff lines, retaining its native findings/overall_correctness/explanation/confidence schema; `security-reviewer` is only for a compatible source-security slice in its own schema. Overriding a schema does not override patch-only role intent. Prefer fewer substantial workers to many tiny ones. Read and apply `skill://principle-separate-before-serializing-shared-state`. One writer per branch/workspace and explicit exclusive paths. Real-surface verification uses `skill://control-ui` or `skill://control-cli` with the required local browser, terminal, simulator and authorized credentials. Do not claim isolated workspaces inherit usable browser state, ports or authentication. A separately configured different-model verifier is useful when available; same-model independent runs must be described honestly.

Use one batch for genuinely independent substantial tasks. Bound active work by the smaller of the actual concurrency/job limits, ownership boundaries, and what one drain can absorb, initially roughly ten units. No batch may exceed the exposed tool cap. Queued items are not running. Plan mode is read-only and rejects isolation controls; obtain the required execution approval rather than bypass it. Honor runtime and request limits. Children skip builds, tests, lint and format during concurrent editing. Assign verification on stable owned heads after mutation, not while siblings are still editing them.

Native task isolation may auto-apply captured changes, or commit/cherry-pick in branch mode. For unaccepted program work use documented `eval agent(prompt, { isolated: true, apply: false, merge: false })` controls and preserve the returned patch and report artifacts before isolation teardown. If those controls are unavailable, use read-only proposals or serialize an explicitly approved workspace boundary; disclose reduced concurrency. Never apply all competing alternatives. Read and apply `skill://arena` for contested designs and select the base before integration. Read and apply `skill://swarm` for coverage partitions.

#### Parent-owned durable records

Create a scoped `local://orchestrate/<project-slug>/` notepad area. This is file-backed session work, not a new runtime. The parent is the only shared-record writer. Children return facts in `agent://<returned-id>` and uniquely owned receipts; the parent accepts and records them. Link the actual resolved artifact location and session pickup information so a later session can locate it. Session-local URIs are not global discovery keys or an indefinite retention guarantee.

- `preferences.md` contains numbered standing orders, one constraint per line. Include objective, model/role policy, stack shape and count, verification bar, forbidden paths, ownership, authorization and escalation rules. Include its current contents in every spawn and substantive follow-up, or require a read of its exact URI with a recorded version. Read and apply `skill://principle-encode-lessons-in-structure` when a correction recurs. Encode the durable constraint before repeating work.
- `overview.md` is an append-only PR/issue and delivery history, not a mutable narrative pretending to be current state.
- `units.tsv` is the work-item DAG and ownership table. Each row has `id`, `track`, `state`, `depends_on`, `owner_id`, `job_id`, `branch`, `base_sha`, `head_sha`, `pr`, `write_scope`, `brief`, `report`, `attempt`, `last_evidence_at`, and `blocker`. IDs are unique. Dependencies point to existing units and must be acyclic. Preserve canceled, failed and abandoned attempts instead of silently overwriting history.
- `frontier.json` is the computed topology snapshot. Store `generation`, ordered PRs with branch/base/head/state and dependencies, `lowestUnmerged`, verified contiguous ceiling and topology owner. See Stack safety.
- `ledger.tsv` retains one accepted verdict per PR/head key plus superseded evidence in the history. Fields are `pr`, `sha`, `base_sha`, `patch_id`, `verdict`, `evidence`, `verifier`, `ts`. Local unpublished units use their explicit unit key until a PR exists; do not fabricate numbers.
- `inbox.tsv` is the parent's durable list of completion pointers. Fields are timestamp, returned agent ID, job ID, unit, reported status, report URI and reconciled state. It is not a mailbox replacement. Native notifications and `hub` provide delivery.
- `gates.md` records gate ID, question, options, default on no answer, owner, status and actual resolution. No answer never authorizes a sensitive or destructive write.
- `decisions.tsv` is the decision trail. Read and apply `skill://show-me-your-work` and its actual schema. Do not invent another trace format.
- `status.md` is derived at each drain from units, ledger, frontier and gates. Include counts, changes since last drain, and open gates. Do not hand-maintain duplicate state.
- `pickup.md` contains objective, completed/pending units, authorization, records and receipts, repository/workspace paths, known agent/session IDs, process names, current frontier generation and exact next action.

The parent todo displays phases and actionable work. It is not the delivery ledger: completed items can disappear on resume and only one todo item is active. Keep simultaneous owner states and completed proof in the tables. Use native read/edit/write for records, and an incremental eval cell for derived counts if needed. Do not build a scheduler or persistence subsystem to manage them.

#### The brief

A field you cannot fill is work you have not scoped. Shared batch context has `# Goal`, `# Constraints`, and `# Contract`. Each assignment has `# Target`, `# Change`, and `# Acceptance`, carrying these fields.

```text
GOAL         one executable outcome for a stranger without chat access
SCOPE        allowed and forbidden paths; exclusive branch/workspace; integration owner
CONTEXT      exact file, PR and upstream agent:// report pointers; necessary facts
ACCEPTANCE   observable criteria, one per line
VERIFY       exact commands or skill://control-* recipe; runtime needs and known gotchas;
             no project-wide validation during concurrent mutation
TIMEBOX      expected runtime and actual limit; partial report on expiry
FORBIDDEN    no out-of-scope fixes, no topology mutation by workers, no unauthorized
             commit/push/merge/deletion/install, no recursive orchestration or child todo
REPORT       unit, status, branch/base/head, PR, patch/report paths, verdict,
             actual runs and evidence, deviations, failure mode, follow-ups
STANDING     current standing orders verbatim, with their recorded version
```

Size briefs to real work. Do a one-command or two-line unit inline rather than paying a full delegation scaffold. A track lead additionally gets its unit list, rollup boundary and format: per child ID, state, PR, SHA, verdict and one line; then track status and frontier delta. Relay upstream artifacts into downstream briefs. Ordering alone is not context. Children may use `hub` for precise coordination with known peers but cannot transfer ownership or change the DAG without parent acceptance. Audit one sampled worker brief per track per wave alongside that wave. Failure stops the next refill and corrects the track-level contract, not merely the one worker. A follow-up is a consolidated assignment with standing orders, not a chain of partial reminders. Use fresh tasks when scope has changed or an isolated child cannot be revived.

#### Steps

1. **Frame.** State a countable done predicate, such as all 126 units delivered with current-head behavioral evidence. Quantify units, effort, expected stacks, time constraints, runtime/spawn limits and permitted delivery operations. Collapse to direct work when one session suffices. Name project-specific tracks. Read and apply `skill://arena` for a contested decomposition or one-way door before the pilot. Present framing once; reversible authorized preparation proceeds. Schedule integration against the actual deadline. By roughly 70 percent of an explicit wall-clock budget, stop adding work and concentrate on verified delivery. Do not call an unfinished predicate done because time expired.
2. **Initialize native state.** Open parent todo, the decision trail, standing orders and DAG before spawning. Seed the frontier from observed repository and forge state. Record active/resume boundaries and ownership. No runtime installation or bootstrap is required.
3. **Pilot.** Push one unit through brief, worker, proof, stack entry, ledger and authorized integration/publication. If merge authority is absent, the pilot ends at verified merge-ready, not an unauthorized merge. Falsify the brief template, verify recipe and unit size while one unit bears the risk. Repair the contract from evidence before fan-out. For cheap identical units, the first ordinary unit with its inline verify command is the pilot. Dedicated independent verifier/audit stages are for novel, expensive or high-blast-radius shapes.
4. **Scale.** Dispatch eligible independent units in bounded asynchronous waves. Refill free capacity after accepted completions rather than waiting for the slowest unrelated child. If async execution is disabled, use bounded synchronous batches and disclose the constraint. Recompute ready work after every drain and relay upstream outputs. A unit is eligible only when dependencies have reached their required verified/integrated state, inputs match the recorded upstream SHA, acceptance is complete, required tools/credentials and authority exist, its branch/path ownership is free, and capacity remains. Mere child completion is not dependency acceptance. A failing sampled brief stops the next refill.
5. **Drain.** Follow the discipline below. Inspect bottlenecks at each wave boundary. Count ready, blocked, running, needs-verify, verified and integrated units. Name whether research, writing, proof, topology, forge checks or operator authority is limiting flow. Reallocate to the limiting eligible stage, shrink oversized units or repair bad contracts. Do not increase fan-out into a blocked frontier or consume more capacity than the parent can drain.
6. **Integrate continuously.** Start with the first verified unit alongside remaining waves. Use one integration owner per stack, with scoped implementation tasks for code conflicts. Keep the frontier green before upper-stack work. Only accepted, dependency-contiguous verified slices enter the delivered branch/stack. Native patch capture or application is not publication, PR merge or proof. Push and merge only within explicit authorization. Recompute the frontier after confirmed topology/head changes and each merge.
7. **Close.** Drain final results and reconcile every spawn to a terminal row: done, abandoned, canceled or late-result-reconciled. Confirm the predicate on the real artifact and every delivered PR's current verdict. Audit the trail with `skill://show-me-your-work`, including its independent review and honest configured-model limits. Encode recurring corrections in standing orders or briefs. Preserve records as the postmortem and publish only authorized artifacts. If a genuine boundary blocks completion, write the exact handoff and report it rather than invent completion.

#### Queue and drain

- A notification appends its returned IDs and `agent://` pointer to the parent inbox, then the parent finishes its current critical section. Do not deep-review a diff in a drain. Review-needed work becomes a scoped verification item.
- Drain after critical sections, track rollups, observed frontier events and before reports. Critical sections include brief authoring, topology operations, conflict decisions, gates, ledger and frontier updates. Take a finite inbox snapshot; arrivals during it belong to the next drain.
- Native results auto-deliver. `hub jobs` or `hub wait` can consume settled delivery; do not expect a duplicate notification. Job IDs expire shortly after settlement, so persist agent IDs and output URIs. `hub wait` returns on the first event and is only for when useful work is exhausted. Use `hub inbox` for messages and `hub list` for actual known peers, not polling to feel busy.
- Classify pointers as landed, needs-verify, failed, late/zombie or noise. Accept reports only against current ownership, dependencies and SHA. Update units, ledger, frontier and parent todo; derive status; dispatch the next eligible batch. Every child is arrived, replaced or explicitly absorbed. Do not silently redo a missing scope.
- A drain ends with three lines: counts against states, what changed, gates open. Detail stays in status. The full reply contract applies at checkpoints and close.

#### Stack safety

- Compute frontier from the actual selected forge and fetched refs, not narration or another CLI's private tracking. Default to `gh`; select Origin only after reading its installed help and confirming the required operations and repository support, then use its documented interface consistently. An executable name alone does not establish its API. Record any fallback. Preserve the intended base-branch DAG and compare it with observed parent/base/head state. Any mismatch, missing PR or ambiguous topology blocks mutation until reconciled. Increment generation on observed merge or topology/head changes.
- Exactly one topology owner per stack. Record the holder in standing orders. Workers never rebase, retarget or force-push. A topology handoff must release prior branch ownership before edits. Read and apply `skill://sky-mode/playbooks/babysit.md` for one babysitter per immutable frontier generation; it reports conflicts upward instead of changing topology.
- Retargets, closes, rebases and merges are scoped units with explicit authority. Closing a base can orphan descendants. For permitted rewritten pushes, inspect the remote expected ref/SHA and use an exact force-with-lease; a changed remote invalidates the operation. Never overwrite another writer.
- Read and apply `skill://sky-mode/playbooks/shipping.md`. Land only the contiguous verified run from the lowest unmerged PR, one PR at a time. Record verdict base/head and stable patch-id. A changed patch needs new proof; unchanged patch-id can preserve code verdict but never stale CI or mergeability. Recompute after each confirmed merge and stop at the first unverified gap.
- Keep one bounded retrospective watch for reverts, post-merge CI failures and orphaned follow-ups. Supervise actual watcher processes with `hub`, not an autonomous scheduler.

#### Verification and delivery ledger

Scale proof to the unit. A cheap deterministic command may run inline on a stable slice, with its actual receipt accepted by the parent. Dedicated independent verifiers earn their place for expensive, judgment-heavy or high-blast-radius units, not merely echoing one command. Behavioral changes need real-surface proof via `skill://principle-prove-it-works`; CI green is only an input.

Ledger verdicts are `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, or `verifier-failed`. Record the actual surface in evidence, including CLI proof when applicable. `type-check-only` cannot pass behavioral work. Blocked is not passed; retry when the environment heals. Failed gets a fix unit, not blind re-verification. A worker may self-report, but independent verifier evidence overrides it on the same key. New head SHA invalidates its verdict unless the Shipping patch-id procedure explicitly preserves code proof while refreshing current-head checks. Record that transition. The ledger, not memory, answers whether a slice is verified.

Externalize each accepted unit immediately. Retain captured patch, current head, authorized branch publication, verifier report and receipts at known durable paths. The parent inspects full `agent://` outputs and receipts before normalizing returned evidence into the shared ledger. Preserve bounded patch/security reviews in their native schemas alongside the ledger; patch correctness alone cannot establish runtime coverage or a passing behavioral verdict. A worker cannot claim done for code trapped in a teardown workspace. No row becomes delivered until its actual required delivery operation and evidence exist.

#### Liveness, failure and durable pickup

- Probe facts through `hub jobs`, `hub list`, known `agent://` outputs, forge state, refs and records. Do not message an idle agent merely to test liveness; `hub send` can revive it into a new turn. Transcript mtime is not progress. Read `history://<known-id>` only for the task session whose identity was returned, never unrelated histories.
- A silent death gets an inbox postmortem with unit, failure mode, last evidence and options. Replan as evidence arrives, without waiting for full quiescence.
- Retry by cause. A cap hit or memory exhaustion gets smaller scope. A network interruption can retry the same scoped request. A tool error gets a corrected tool/environment contract, optionally another configured agent after diagnosing the failure. Unknown failure gets one retry. At most two retries per unit, then mark abandoned and replan around it. Do not hide the resulting coverage gap or relax the predicate.
- A late result must reconcile current frontier, ownership and ledger before acceptance. Salvage unique findings in a fresh unit, never blindly merge a stale patch. Isolated sessions are not revivable after teardown; preserve their artifacts and dispatch fresh.
- If continued spawning would spread bad upstream output, invalid acceptance or broken infrastructure, put STOP atop the standing orders and stop refilling. Let safe in-flight units finish to artifacts, or issue zero-writes/cancel when continued mutation is unsafe. Fix the cause before clearing the stop. Operator hold takes precedence immediately.
- Bound parent infrastructure retries too. Repeated tool aborts require a durable handoff, not an endless retry loop. Record done/pending work, exact artifacts, observed failures and the next concrete operation. A blocker is not successful completion.
- A long program requires an active parent or an explicitly resumed user session. `hub start` supervises watcher/server processes; observe readiness, use logs and wait for events, and use send/stop for control. For a 30-minute audit fallback, start named `sleep` with `args: ["1800"]`, observe exit and rearm during the active session. Timers do not launch agent turns. Processes default to teardown after the last client exits. Opt-in persistence does not keep reasoning sessions alive and must not be assumed indefinite.
- Before stopping, use `skill://sky-mode/playbooks/pause-safely.md`. On explicit resume, use `skill://sky-mode/playbooks/session-pickup.md`, read preferences, pickup, units, ledger and trail, then compare actual refs/forge/process state with the saved frontier. Persisted transcript entries are not live jobs. Job handles and eval kernels are process-local. Do not assume old IDs are messageable; consult the live roster and use saved output/session artifacts. Reconstruct pending briefs from accepted evidence, avoid redoing completed work, drain and continue from the first eligible unit. No automatic restart, hidden background session or custom lock recovery is promised.

#### Escalation

Batch genuine human gates into the status page: missing permission for external or destructive actions, shared-branch force-pushes, deployment, deletion, closing another person's PR, product/preference decisions experiments cannot settle, standing orders contradicted by reality, and a program dead end that survived replanning. Park each gate with options and a safe no-answer default, then work around it when possible. Silence never authorizes the action.

Do not ask about authorized reversible frontier mechanics, scoped retries, CI-flake triage, review triage or whether to keep going. Refuse forbidden scope and continue. Mid-run discoveries fix only what blocks the frontier within authority; everything else becomes a follow-up, not scope leaked across dozens of PRs.

**Reply:** predicate and counts from units/ledger; tracks and accepted deliveries; ordered frontier PRs and SHAs; verdict summary and evidence; abandoned work and reasons; human gates; current bottleneck and next eligible wave; records and trail paths; PR links; and exact pickup instructions if paused. Numbers come from the records, not narrative estimates.
